## 1. 项目定位

### 1.1 解决的问题

半导体工艺文档数量多、术语密集、章节层级深。传统关键词搜索只能找到文件，不能直接给出可核对的答案。通用大模型能生成流畅回答，但容易编造工艺参数、设备型号和结论。

这个项目把 430 篇 Markdown 技术文档变成可对话的知识库，核心目标不是答得多，而是答得准、答得有依据、答不出来时能说清楚。

### 1.2 角色与场景

| 角色 | 入口 | 核心动作 |
|---|---|---|
| 访客、工程师、学生 | `/` 问答页 | 新建会话、提问、看流式回答、展开引用、查看检索过程、评价回答 |
| 管理员 | `/admin` 管理台 | 登录、上传文档、重建索引、删除文档、查看任务、调检索参数、做问答测试、审计消息 |

典型场景：

1. 领域问题命中本地库，返回带 `[1]`、`[2]` 角标的回答。
2. 本地召回不足，查询改写最多两次再检索。
3. 改写后仍无相关文档，转 Tavily 联网搜索，再基于联网结果生成。
4. 非半导体问题，路由节点判断走联网。
5. 管理员上传新报告，后台任务自动解析、切片、向量化，完成后可立即检索。
6. 检索效果不佳，管理员在调试页调整 `top_k`、阈值和过滤表达式，直接看命中与得分。
7. 生成模型不可用，系统退回抽取式回答，把命中最高的原文片段交给用户。

### 1.3 本期范围

本期包含：

- Markdown 文档入库，增量上传，单篇重建，删除，全量影子集合重建。
- 稠密向量加 BM25 稀疏向量的混合检索。
- LangGraph 问答编排，查询改写，文档评分，生成校验，联网兜底。
- WebSocket 流式输出，节点时间线，引用溯源，用户评价。
- 会话、消息、引用、任务、文档元数据持久化。
- 管理台六个业务标签：总览、文档、任务、检索调试、问答测试、消息审计。
- 健康检查、统计概览、限流、统一异常响应。

本期不做：

- 人工客服与坐席转接。
- PDF、Word、扫描件与 OCR，当前只接收 `.md` 与 `.markdown`。
- 多租户、细粒度权限、合规审计。
- 模型微调与重排模型训练。
- 分布式 Milvus 集群、多副本高可用、跨机房容灾。
- 前端组件库，样式沿用参考项目的原生 CSS 风格。

### 2.3 两个数据主键

系统用两个标识把不同存储层对齐：

- `doc_uid`，32 位字符串，是文档在 MySQL、Milvus、引用表之间的业务主键。
- `id`，数据库自增主键，用于会话、消息、引用和任务的表内定位。

`doc_uid` 不随文档重建而改变。删除后重新上传同一文件时，系统复用原 `doc_uid`，避免 `file_hash` 唯一约束挡住恢复流程。

### 3.2 关键取舍

| 决策 | 原因 | 代价 |
|---|---|---|
| 直接使用 `pymilvus`，不经过 `langchain-milvus` | Milvus 3.0 与 LangChain 封装存在连接管理兼容风险，直接调用可以精确控制字段、BM25、别名与 RRF | 需要自己维护集合、索引和检索代码 |
| MySQL 存元数据，Milvus 只存切片 | 关系查询、任务状态、审计统计放 MySQL 更稳；向量检索放 Milvus 更专业 | 跨库一致性要靠 `doc_uid` 与流水线校验 |
| 物理集合加别名 | 全量重建时先写新集合，校验通过后再切别名，旧集合可保留回退 | 多了一层间接寻址与指针文件 |
| LangGraph 而不是手写 if else | 条件边、循环、节点 trace 和终止语义清晰，便于调试与扩展 | 图状态和递归上限要学会调 |
| `score_threshold` 默认 0 | RRF 单路得分上限约 `1/100`，设 0.1 会过滤掉全部结果 | 检索结果依赖后续文档评分与生成校验兜底 |
| 评分模型也用 `qwen-plus` | `qwen-turbo` 在评分场景频繁 429，换模型比反复重试更稳 | 评分成本略高 |
| 前端不引组件库 | 页面规模不大，原生 CSS 更轻，视觉可控 | 表格、弹窗、分页都要自己写 |
| 重活放线程池 | 嵌入、Milvus、LLM 都是同步客户端，直接阻塞事件循环会拖垮 WebSocket | 线程与连接池需要限流和隔离 |

### 4.4 启动装配

`semikb/main.py` 的 lifespan 做四件事：

1. 初始化 MySQL 连接池。
2. 调用 `TaskDao.recover_stale`，把上次进程留下的 `queued` 与 `running` 任务标记为失败，消息为服务重启，任务中断。
3. 确保 Milvus 集合存在，按 `active_collection.txt` 和别名恢复当前集合。
4. 把管理端 WebSocket 广播所需的事件循环挂到 `AdminWsManager`。

随后挂载 CORS、注册异常处理器、包含六组路由、挂载 `/assets` 静态目录。

### 4.5 单例与进程内状态

大量组件是单例：`Config`、`DbPool`、`MilvusStore`、`AuthService`、`ChatService`、`AdminService`、`RAGRunner`、`IngestPipeline`、`TaskQueue`。

进程内状态包括：

- `ChatService` 的 8 并发信号量与按会话的 busy 集合。
- `AuthService` 的令牌黑名单。
- `RateLimiter` 的滑动窗口计数。
- `ChatWsManager` 的连接计数。
- `AdminWsManager` 的 WebSocket 集合与事件循环。

这些状态在单进程内有效。一旦启动多进程，黑名单、限流和 WebSocket 广播都会分裂，必须换成 Redis 或粘性会话。

### 4.6 并发模型

| 场景 | 机制 | 上限 |
|---|---|---|
| 用户同时提问 | `asyncio.Semaphore` | 8 |
| 同一会话连续提问 | busy 集合串行化 | 每会话 1 条 |
| 管理端入库任务 | `ThreadPoolExecutor` | 2 |
| 批量导入脚本 | 独立线程池 | 默认 4 |
| MySQL 连接 | DBUtils 连接池 | 最小 2，最大 10 |
| 单次问答外层等待 | `asyncio.wait_for` | 90 秒加 5 秒 |
| LangGraph 递归 | `recursion_limit` | 20 |

## 5. 数据层设计

### 5.1 数据关系

```text
t_session 1 ───── n t_message 1 ───── n t_citation
                                     │
                                     └─ doc_uid 指向文档

t_document 1 ───── n t_ingest_task       逻辑关联，无外键
t_document 1 ───── n Milvus chunk        逻辑关联，按 doc_uid 对齐
```

### 5.2 六张表

| 表 | 作用 | 关键字段 | 当前行数 |
|---|---|---|---|
| `t_admin` | 管理员账号 | `username`、`password_hash`、`salt` | 1 |
| `t_session` | 问答会话 | `visitor_name`、`status`、`turn_count`、`last_active_at` | 11 |
| `t_message` | 消息与回答审计 | `role`、`content`、`source`、`route`、`trace_json`、`verified`、`rating` | 10 |
| `t_citation` | 回答引用 | `message_id`、`doc_uid`、`chunk_index`、`rank`、`snippet` | 12 |
| `t_document` | 文档元数据 | `doc_uid`、`file_hash`、`status`、`chunk_count`、`milvus_collection` | 430 |
| `t_ingest_task` | 入库任务 | `task_type`、`status`、`progress`、`total_chunks`、`done_chunks` | 1 |

### 5.3 状态枚举

文档状态：

| 状态 | 含义 |
|---|---|
| `pending` | 已接收，等待解析 |
| `parsing` | 正在解析 Markdown |
| `indexing` | 正在嵌入与写 Milvus |
| `ready` | 已入库，可检索 |
| `failed` | 入库失败，保留错误信息 |
| `deleted` | 已标记删除，源文件与向量可能已清理 |

任务状态：

| 状态 | 含义 |
|---|---|
| `queued` | 已进入队列 |
| `running` | 正在执行 |
| `succeeded` | 成功 |
| `failed` | 失败 |
| `cancelled` | 枚举存在，当前没有取消入口 |

消息来源：

| 来源 | 含义 |
|---|---|
| `vectorstore` | 本地知识库 |
| `web_search` | Tavily 联网结果 |
| `direct` | 问候、身份或能力询问的固定介绍，不检索 |
| `fallback` | 无结果或链路失败后的固定兜底 |
| `extractive` | 生成失败后直接拼接原文片段 |

### 5.4 关键约束

| 约束 | 实现 | 影响 |
|---|---|---|
| 文档唯一 | `t_document.file_hash` 唯一 | 同一内容不能重复入库 |
| 软删除 | `status='deleted'`，不物理删除行 | 可复用 `doc_uid` 重新上传 |
| 引用级联 | `t_citation.message_id` 外键 `ON DELETE CASCADE` | 删消息会连带删引用，当前没有删消息接口 |
| 保留字 | `t_citation.rank` 查询与写入必须使用反引号 | 否则 MySQL 解析失败 |
| 任务无外键 | `t_ingest_task.doc_uid` 只是逻辑关联 | 删除文档不会自动删任务 |
| 单次事务 | 每个 DAO 调用用连接上下文提交或回滚 | 跨表流程不是原子事务 |

### 5.5 事务与一致性

`DbPool.cursor` 的上下文管理器在退出时 `commit`，异常时 `rollback`。这保证单条 SQL 或单次 DAO 调用的一致性，但不保证跨 DAO 的完整业务事务。

典型非原子点：

- 上传时先写文件与文档行，再提交任务；进程在中间崩溃会留下 pending 文档。
- 删除时先把文档标记为 deleted，再异步删向量；任务失败会留下已删除状态与残留向量。
- 全量重建逐篇更新文档状态，最后才切别名；中途失败没有自动回滚。

### 5.6 统计口径

`StatsService.overview` 以最近 7 天为默认窗口，返回：

- 文档总数、ready 数、failed 数、切片数。
- 会话总数、活跃会话、今日新增。
- 问答总数、今日问答、窗口内问答。
- 校验率、引用率、满意率、改写率、重生成率。
- 平均时延、P95 时延、样本数。
- 来源分布、按日趋势、热门引用文档、待处理任务数。

当前窗口只有 4 条知识问答样本，校验率 1.0、引用率 1.0、满意率 1.0、改写率 0.25、重生成率 0.25、平均时延 13087 毫秒。直接回答不计入问答与质量指标，避免问候把引用率拉低。

## 6. Milvus 向量层

### 6.1 集合与别名

| 项 | 值 |
|---|---|
| 服务端 | `http://127.0.0.1:19530`，Milvus 3.0.2 |
| SDK | `pymilvus 3.0.2` |
| 物理集合 | `semi_kb_chunks_v1` |
| 业务别名 | `semi_kb_chunks` |
| 集合指针 | `data/active_collection.txt`，内容 `semi_kb_chunks_v1` |
| 一致性级别 | `Strong` |

读取路径使用别名，写入路径使用当前物理集合。重建时创建 `semi_kb_chunks_v2`，写入并校验后把别名切到 v2，再更新指针文件与文档表中的 `milvus_collection`。

### 6.2 字段设计

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `INT64`，自动主键 | Milvus 内部主键 |
| `text` | `VARCHAR(12000)` | 切片正文，启用 jieba 分词与 `cnalphanumonly` 过滤 |
| `category` | `VARCHAR(1000)` | 当前固定为 `content`，检索时按此过滤 |
| `source` | `VARCHAR(1000)` | 文档文件名或来源地址 |
| `filename` | `VARCHAR(1000)` | 原始文件名 |
| `filetype` | `VARCHAR(1000)` | 当前固定 `md` |
| `title` | `VARCHAR(1000)` | 标题层级路径 |
| `category_depth` | `INT64` | 标题深度 |
| `doc_uid` | `VARCHAR(64)` | 文档业务主键 |
| `chunk_index` | `INT64` | 文档内切片序号 |
| `sparse` | `SPARSE_FLOAT_VECTOR` | BM25 稀疏向量 |
| `dense` | `FLOAT_VECTOR`，`dim=1024` | `text-embedding-v4` 稠密向量 |

### 6.3 索引与 BM25

| 索引 | 字段 | 类型 | 参数 |
|---|---|---|---|
| `sparse_inverted_index` | `sparse` | `SPARSE_INVERTED_INDEX` | 度量 `BM25`，算法 `DAAT_MAXSCORE`，`bm25_k1=1.2`，`bm25_b=0.75` |
| `dense_hnsw` | `dense` | `HNSW` | 度量 `IP`，`M=16`，`efConstruction=64` |

BM25 函数名为 `text_bm25_emb`，输入 `text`，输出 `sparse`。写入切片时只需要提供正文与稠密向量，稀疏向量由 Milvus 函数自动生成。

### 6.4 混合检索链路

```text
用户问题
  ├─ DashScope 嵌入 → 1024 维 dense 向量
  └─ 原始文本 → BM25 sparse 查询
        │
        ▼
Milvus hybrid_search
  ├─ dense AnnSearchRequest：HNSW，候选 20
  ├─ sparse AnnSearchRequest：BM25，候选 20
  ├─ RRF 融合：k=100
  ├─ 过滤：category == "content"
  └─ 取 top_k=4
        │
        ▼
LangChain Document 列表
metadata: score、doc_uid、filename、title、chunk_index、category、url、source
```

### 6.5 三个已验证的环境结论

| 问题 | 结论 | 处理 |
|---|---|---|
| Milvus 3.0.2 创建 `TEXT` 字段失败 | 当前服务端未开启 `common.storage.useLoonFFI`，报 StorageV3 错误 | 实际字段改为 `VARCHAR(12000)`，BM25 仍正常 |
| RRF 分数设 0.1 后检索为空 | RRF 单路得分上限约 `1/100`，0.1 高于可达上限 | `score_threshold` 保持 0，不做绝对阈值过滤 |
| `qwen-turbo` 评分频繁 429 | 评分模型限流导致校验链路不稳 | 评分模型切换为 `qwen-plus`，最多 1 次重试，限流时保留召回结果 |

### 6.6 全量重建的影子集合流程

```text
读取全部 ready 文档
  → 计算下一个物理集合名 vN
  → 创建 vN，不切别名
  → 逐篇 run_document
       collection=vN
       persist_collection=False
       update_task=False
       flush_collection=False
       verify_count=False
  → 全部完成后 flush 一次
  → count_total(vN)
  → set_alias(vN, semi_kb_chunks)
  → 写 active_collection.txt
  → 更新全部文档的 milvus_collection
  → 任务成功
```

这个设计避免重建期间污染线上集合，也避免每篇文档都触发 flush。代价是重建期间新旧集合同时存在，磁盘占用会短时翻倍。

### 6.7 读写一致性

- 检索走别名，始终读当前活动集合。
- 文档详情与切片预览按该文档的 `milvus_collection` 查询，避免重建后读错集合。
- 删除按文档自身的 `milvus_collection` 删除，不会误删其他集合。
- 计数校验分别使用 `count_doc` 与 `count_total`，后者优先 `count(*)`，失败时退回集合统计。

## 7. 文档入库链路

### 7.1 总流程

```text
上传或批量脚本
  → 文件校验：扩展名、大小、重复哈希
  → 文件落盘 data/docs/{doc_uid}_{filename}
  → MySQL 文档记录 pending
  → MySQL 任务记录 queued
  → 线程池执行 IngestPipeline.run_document
  → 解析 Markdown
  → 标题栈与语义块
  → 切片与短片段合并
  → 批量嵌入，10 条一批
  → 批量写 Milvus，50 条一批
  → flush 与计数校验
  → 文档 ready，任务 succeeded
  → 管理端 WebSocket 推送
```

### 7.2 Markdown 解析

`parse_markdown` 的实际优先级：

1. 读取全文，统一换行，压缩空白。
2. 取第一个 `#` 到 `######` 标题作为文档标题，没有标题就用文件名。
3. 使用自研标题栈解析器，保留完整层级路径，例如 `光刻 > EUV 光源 > 锡液滴`。
4. 自研解析没有产出时，才尝试 `unstructured`。
5. 仍然没有产出时，把整篇文本作为一个块。

标题栈遇到新标题时先 flush 当前块，再按级别裁剪栈。只有标题没有正文的块会被丢弃，避免产生十几个字的空切片。

### 7.3 切片规则

| 参数 | 值 | 实际行为 |
|---|---|---|
| `chunk_char_limit` | 5000 | 单个语义块不超过 5000 字符时整段保留 |
| `chunk_hard_max` | 2400 | 只有超过 5000 字符的块才按 2400 字符切分 |
| `chunk_overlap` | 120 | 切分时相邻片段保留 120 字符重叠 |
| `min_chunk_chars` | 80 | 小于 80 字符的片段合并到前一个切片 |
| 分隔符 | 段落、换行、句号、分号、逗号、空格 | 优先按语义边界切 |

需要特别注意：`chunk_hard_max=2400` 不是所有切片的绝对上限。一个 3000 字符的完整小节会保留为一个 3000 字符切片。只有超过 5000 字符的块才会被 2400 字符切分器切开。最终会出现超过 2400 字符但不超过 5000 字符的切片，这是当前设计的有意结果。

430 篇文档最终产出 2168 个切片，平均每篇约 5.04 个切片。

### 7.4 嵌入与写入

每个切片写入 Milvus 的字段：

```text
text = 切片正文
category = content
source = 文档文件名
filename = 文档文件名
filetype = md
title = 标题层级路径
category_depth = 标题深度
doc_uid = 文档业务主键
chunk_index = 文档内序号
dense = text-embedding-v4 生成的 1024 维向量
```

嵌入批量为 10 条，写入批量为 50 条。写入前会先按 `doc_uid` 删除旧向量，保证单篇重建不会留下重复切片。

### 7.5 任务队列与并发

| 入口 | 并发 | flush 策略 | 计数校验 |
|---|---|---|---|
| 管理台上传 | 线程池 2 | 每篇 flush 一次 | 单篇校验 |
| 单篇重建 | 线程池 2 | 每篇 flush 一次 | 单篇校验 |
| 全量重建 | 线程池内串行 | 全部完成后 flush 一次 | 总量校验 |
| 批量脚本 | 默认 4 线程 | 全部完成后 flush 一次 | 最终总量校验 |

批量脚本只在结束时 flush 一次，避免 430 次 flush 拖慢导入。代价是进程中途被杀时，未 flush 的数据可能不可见，需要用最终计数校验补一道保险。

### 7.6 上传校验

`AdminService.upload_documents` 做六层校验：

1. 一次最多 20 个文件。
2. 单文件不超过 5 MB。
3. 只接收 `.md` 与 `.markdown`。
4. 文件名经过 `safe_filename` 清理路径成分。
5. 本次上传内部按 SHA-256 去重。
6. 数据库中已存在且未删除的同哈希文件直接拒绝。

如果同哈希文档已经处于 `deleted` 状态，系统复用原 `doc_uid`，覆盖源文件，重置状态与切片数，再提交新的上传任务。这条路径已经实测：上传、删除、重新上传、再次删除全链路成功。

### 7.7 删除、重建与失败语义

单篇删除：

```text
文档先标记 deleted
  → 任务 queued
  → 按文档记录中的集合删除 doc_uid 对应向量
  → flush
  → 任务 succeeded
```

单篇重建：

```text
检查是否有进行中的任务
  → 文档置 parsing
  → 任务 reindex
  → 按当前活动集合删除旧向量
  → 重新解析、切片、嵌入、写入
  → 计数校验
  → 文档 ready
```

失败语义：

- 单篇解析或写入失败，文档置 `failed`，任务置 `failed`，错误信息截断 500 字符。
- 向量写入在计数校验之前，校验失败时可能已有部分切片写入。重新执行重建会先按 `doc_uid` 删除旧向量，再重写，能够自愈。
- 删除是先改状态再异步删向量。如果删除任务失败，文档仍是 deleted，Milvus 中可能残留向量。当前没有自动补偿。
- 全量重建中途失败时，旧别名不动，线上仍可服务。但已经处理的文档状态可能先变成 ready，影子集合没有自动清理，也没有回滚文档状态。

## 8. RAG 问答图

### 8.1 图结构

```text
route_question
  ├─ direct → direct_answer → END
  ├─ vectorstore → retrieve → grade_documents
  │                    ├─ 有文档 → generate → grade_generation
  │                    ├─ 无文档且未改写满 → transform_query → retrieve
  │                    └─ 无文档且改写用尽 → web_search → generate
  └─ web_search → web_search → generate → grade_generation

grade_generation:
  useful → END
  not supported → generate
  not useful → transform_query
  give_up → END
```

直接回答分支只运行 `route_question` 与 `direct_answer`，没有 retrieve、文档评分、生成校验，也不会产生引用。

### 8.2 八个节点

| 节点 | 输入 | 主要动作 | 输出 |
|---|---|---|---|
| `route_question` | 原始问题 | 半导体关键词短路，识别寒暄，否则评分模型判断走向 | `route`、`route_method`、`direct_intent` |
| `direct_answer` | 原始问题与寒暄意图 | 不查库、不调模型，返回固定介绍 | `generation`、`source=direct` |
| `retrieve` | 当前问题 | 嵌入查询，Milvus 混合检索 4 条 | `documents` |
| `grade_documents` | 问题与候选文档 | 批量判断相关，失败时逐篇判断 | 过滤后的 `documents` |
| `generate` | 问题、上下文、最近历史 | `llm.stream` 生成回答并推 token | `generation`、`generation_count` |
| `grade_generation` | 文档、问题、回答 | 同时判断 grounded 与 answers_question | `verified`、`verdict`、`terminated_by` |
| `transform_query` | 当前问题 | 改写成更适合检索的问题 | `question`、`transform_count` |
| `web_search` | 当前问题 | Tavily 搜索最多 3 条 | 联网 `documents` |

### 8.3 路由

路由先做关键词短路。配置中有 80 余个半导体领域关键词，包括半导体、芯片、晶圆、光刻、封装、测试、刻蚀、薄膜、沉积、离子注入、CMP、EUV、DUV、GAAFET、FinFET、3D NAND、HBM、CoWoS、TSV 等。

命中任一关键词直接走向量库，节省一次模型调用。未命中时先识别问候、感谢、告别、身份与能力询问，命中后走 `direct`。这一层会去掉语气词、标点和常见礼貌前缀，例如你好、您好、请问、我想问一下。你好，你是谁会识别为身份询问；你好，光刻是什么仍因关键词命中而走本地库，不会被误判为闲聊。

寒暄未命中时才调用评分模型判断 `vectorstore`、`web_search` 或 `direct`。模型失败时默认走向量库，方法标记为 `fallback`。

### 8.4 检索与文档评分

检索固定候选 20 条，RRF 融合后取 4 条。过滤表达式默认 `category == "content"`。

文档评分优先批量一次完成。评分提示要求输出与文档数量一致的 `yes` 或 `no` 数组，每篇文档只截取前 1800 字符。批量结果数量不一致会抛错，进入逐篇评分。

限流处理：

- 捕获到 429、rate limit 或 limit_requests 时，保留全部召回结果，跳过逐篇评分。
- 其他异常逐篇评分。
- 单篇评分也失败时保留该文档，避免外部依赖把整条链路拖死。

这个策略保证可用性，但会把一部分判断责任交给生成校验。评分模型持续不可用时，检索质量会下降。

### 8.5 生成

生成节点使用 `qwen-plus`，`temperature=0`，最多 900 tokens，45 秒超时，流式输出。

上下文格式：

```text
[文档 1] 标题：标题路径 文件：文件名
正文

[文档 2] ...
```

总上下文限制 8000 字符。最近历史取 3 轮，实际是最近 6 条消息，每条截断 300 字符。提示词要求只使用给定上下文，用 `[1]`、`[2]` 标注依据，上下文不足时明确说明缺什么。

生成异常时进入抽取式兜底：取前 2 篇文档，每篇截取 900 字符，拼成带来源标题的原文片段。这条兜底不经过模型，不会再编造，但可读性明显下降。

### 8.6 生成校验与终止语义

校验模型同时输出两个字段：

- `grounded`：回答是否完全基于给定文档事实。
- `answers_question`：回答是否真正解决用户问题。

判定矩阵：

| grounded | answers_question | 次数条件 | 结果 |
|---|---|---|---|
| `yes` | `yes` | 任意 | 通过，`terminated_by=useful` |
| `no` | 任意 | `generation_count < 2` | 回到 `generate` 重生成 |
| `no` | 任意 | `generation_count >= 2` | 放弃，`terminated_by=grounded_failed` |
| `yes` | `no` | `transform_count < 2` | 改写问题再检索 |
| `yes` | `no` | `transform_count >= 2` | 结束，`terminated_by=rewrite_exhausted`，`verified` 仍为真 |

这里有一个容易误读的语义：`verified=true` 只表示 grounded 通过，不保证回答完全解决了问题。要看 `terminated_by` 与 `answers_question` 才能判断完整质量。

校验模型不可用时，改用引用完整性启发式：

- 回答中至少有一个 `[n]`。
- 所有引用编号都在 1 到文档数量之间。
- 回答正文至少 80 字符。
- 同时满足才把 `verified` 置真，`terminated_by=grade_unavailable`。

### 8.7 模型与提示词配置

| 项 | 对话模型 | 评分模型 |
|---|---|---|
| 模型 | `qwen-plus` | `qwen-plus` |
| 温度 | 0 | 0 |
| 最大 tokens | 900 | 220 |
| 超时 | 45 秒 | 30 秒 |
| 重试 | 2 次 | 1 次 |
| 流式 | 是 | 否 |

寒暄与关键词先走规则短路，未命中时路由、批量文档评分、单篇文档评分、生成校验都使用 `with_structured_output`。查询改写和最终回答使用普通 Chat 调用。

### 8.10 降级路径

| 故障 | 行为 | 用户看到的结果 |
|---|---|---|
| 寒暄识别命中 | 直接走固定介绍 | 无检索、无引用、无模型调用 |
| 路由模型失败 | 默认向量库 | 仍可正常检索 |
| 检索失败 | 文档为空，进入改写或联网 | 可能转联网或固定无结果文案 |
| 文档评分 429 | 保留全部召回 | 生成质量可能下降 |
| 文档评分其他异常 | 逐篇评分，仍失败则保留 | 尽量保证链路不断 |
| 生成模型失败 | 抽取式兜底 | 原文片段，带来源 |
| 校验模型失败 | 引用完整性启发式 | 有引用且正文足够时标为已校验 |
| 无结果 | 固定文案 | 明确说明没有可靠依据 |
| 图执行异常 | `fallback` 文案 | 任务标记 `graph_error` |
| 用户外层超时 | `fallback` 文案 | 任务标记 `timeout` |

## 9. REST 与 WebSocket 接口

### 9.1 统一响应

除 WebSocket 和文件页面外，REST 统一返回：

```json
{
  "code": 200,
  "message": "ok",
  "data": {}
}
```

异常映射：

- `AppError` 子类按自身 `code` 返回，限流额外带 `Retry-After`。
- 请求参数校验失败统一 400，消息包含字段路径。
- 未捕获异常统一 500，日志记录完整堆栈，响应不暴露内部细节。

### 9.4 用户 WebSocket

路径：`/api/chat/ws/{session_id}?debug=1`

客户端事件：

```json
{"type": "chat", "content": "EUV 光刻胶的分辨率极限如何突破"}
{"type": "ping"}
```

服务端事件序列：

| 事件 | 时机 | 内容 |
|---|---|---|
| `ready` | 连接成功 | 会话信息 |
| `user_message` | 用户消息落库后 | 完整用户消息 |
| `node` | 节点开始与结束 | 节点名、阶段、耗时、detail |
| `chunk` | 生成模型每输出一段 | `delta` 文本 |
| `message_end` | 回答、引用、trace 落库后 | 完整助手消息 |
| `session_status` | 消息结束后 | 更新后的会话状态 |
| `error` | 参数、限流、冲突或内部错误 | code、message、data |
| `pong` | 收到 ping | 心跳响应 |

`debug=0` 时服务端不推 `node` 事件，但回答、引用与时延仍会落库。

### 9.5 管理端 WebSocket

路径：`/api/admin/ws?token=<token>`

服务端事件：

| 事件 | 时机 | 内容 |
|---|---|---|
| `hello` | 连接成功 | 管理员、待处理任务数、服务器时间 |
| `task_update` | 任务状态变化 | 任务 id、类型、状态、进度、切片数、消息 |
| `document_update` | 文档状态变化 | `doc_uid` |
| `pong` | 收到 ping | 心跳响应 |

客户端每 25 秒发送一次 ping。管理端收到 `task_update` 后原位更新任务列表；任务成功或失败时刷新文档和统计；收到 `document_update` 时刷新当前文档页。

### 9.6 分页契约

文档、任务、消息审计统一使用：

```text
page: 从 1 开始
size: 默认 20，最大 100
total: 服务端返回总数
items: 当前页数据
```

前端根据 `total` 与 `size` 计算总页数，只有大于 1 页时才显示翻页控件。

| 码 | 场景 |
|---|---|
| 400 | 参数校验失败、空问题、问题超过 2000 字、未知消息类型 |
| 401 | 未登录、令牌无效、令牌过期 |
| 404 | 会话、文档、任务、消息不存在 |
| 409 | 会话已关闭、上一条回答仍在生成、重复文件、已有进行中的任务 |
| 413 | 单文件超过 5 MB |
| 415 | 非 Markdown 文件 |
| 429 | 登录、提问、上传、检索调试、问答测试触发限流 |

## 10. 前端问答页与管理台

### 10.1 技术结构

前端是单页应用，只有两个路由：

| 路由 | 页面 | 作用 |
|---|---|---|
| `/` | `ChatView.vue` | 用户问答 |
| `/admin` | `AdminView.vue` | 管理台 |

开发模式端口 5174，Vite 把 `/api` 与 WebSocket 代理到 8010。生产模式由 FastAPI 直接返回 `semikb/static/index.html`，`/assets` 挂载静态资源。

### 10.2 问答页

问答页由六块组成：

| 区块 | 组件 | 功能 |
|---|---|---|
| 顶部栏 | 原生模板 | 品牌、连接状态、管理台入口 |
| 会话列表 | `SessionList` | 历史对话、对话编号、状态、切换会话 |
| 左侧栏 | `QuickQuestions` | 建议问题、当前会话、新建会话 |
| 会话区 | `MessageBubble` | 消息、引用、trace、评价 |
| 流式区 | `TraceTimeline` | 节点时间线、逐字输出、引用角标 |
| 输入区 | 原生 textarea | Enter 发送、Shift 加 Enter 换行、2000 字上限 |

交互流程：

1. 首次进入，先加载 `/api/meta` 与 `/api/chat/sessions`。
2. 读取 `localStorage` 中的会话 ID，有历史时直接拉取最近 100 条消息。
3. 会话活跃则连接 WebSocket；已关闭则进入只读历史态。
4. 无历史或加载失败时新建会话。
5. 发送时先插入乐观用户消息，再通过 WebSocket 发 `chat`。
6. 收到 `user_message` 后用服务端消息替换乐观消息。
7. 收到 `node` 更新节点时间线，收到 `chunk` 拼接流式文本。
8. 收到 `message_end` 把回答放入消息列表，并刷新历史会话列表。
9. 点击赞或踩调用评价接口，失败时回滚本地状态。

历史会话列表在桌面端显示在左侧栏，窄屏端在会话区上方显示同一组件。列表展示的 `conversation_id` 来自该会话首条机器人回复的 `t_message.id`，不是内部 `session_id`。新会话在首条机器人回复落库前不会进入列表。切换已结束会话时输入框锁定，切换活跃会话时重新连接 WebSocket。

问候、感谢、身份或能力询问会直接返回介绍，消息标签显示直接回答，展开回答过程只有问题路由与直接回答两个节点，没有向量检索、文档评分和引用。

流式文本与完整消息都先做 HTML 转义，再把引用角标替换为样式节点。完整消息还支持有限的代码块、行内代码、加粗与二级三级标题，不使用不受控的 Markdown 渲染器。

### 10.3 管理台

管理台登录后显示六个业务标签：

| 标签 | 面板 | 功能 |
|---|---|---|
| 总览 | `OverviewPanel` | 文档、会话、问答、质量、时延、来源、趋势、热门引用 |
| 文档 | `DocumentsPanel` | 上传、筛选、查看详情、切片预览、重建、删除 |
| 任务 | `TasksPanel` | 任务分页、状态、进度、切片数、消息 |
| 检索调试 | `RetrievalPanel` | 查询、`top_k`、阈值、过滤表达式、命中详情 |
| 问答测试 | `QaPanel` | 直接跑完整 RAG，查看回答、来源、trace |
| 消息审计 | `MessagesPanel` | 助手消息分页、来源、时延、校验、评价、引用与 trace |

管理台状态集中在 `stores/admin.js`：

### 10.4 分页组件

`frontend/src/components/PaginationBar.vue` 是三个表格页共用的分页条，支持：

- 统计行：共多少条、每页多少条、当前第几页、共几页。
- 首页、上一页、页码、下一页、末页。
- 当前页高亮与 `aria-current`。
- 页码窗口：始终包含第一页、最后一页、当前页与前后两页；靠近两端时补足 5 个页码。
- 页码之间自动插入省略号。
- 输入框跳转，支持回车与按钮两种触发方式。
- 只有总页数大于 1 时才显示翻页控件。

三个页面的接入方式一致：

```text
PaginationBar
  props: page、size、total、unit
  event: change(page)
  → 父组件调用 store.loadDocuments、loadTasks 或 loadMessages
```

- 管理台标签是组件内状态，不进入 URL。刷新后会回到总览，不能直接分享某个标签页链接。

## 11. 安全、性能与可靠性

### 11.1 认证与令牌

管理员口令哈希：

```text
password_hash = SHA-256(salt + password)
```

当前实现是加盐 SHA-256，`AuthService` 顶部注释里写的 PBKDF 风格只是命名，不是 PBKDF2。校验使用 `hmac.compare_digest`，避免直接字符串比较。

令牌结构：

```text
base64url(payload).base64url(HMAC-SHA256(secret, body))
```

payload 包含管理员 id、用户名、签发时间、过期时间。TTL 8 小时。登出把完整令牌放入进程内黑名单，重启后清空。

### 11.2 限流

| 场景 | 配置键 | 配置值 | 实际代码使用 |
|---|---|---|---|
| 创建会话 | `rate_limit.chat_per_minute` | 20 每分钟 | 按 IP 限制 |
| 单会话提问 | `rate_limit.session_per_minute` | 10 每分钟 | 按会话 ID 限制 |
| 管理员登录 | `admin_login_per_minute` | 5 每分钟 | 按 IP 限制 |
| 上传 | `upload_per_hour` | 30 每小时 | 按管理员 ID 限制 |
| 检索调试 | `retrieval_test_per_minute` | 30 每分钟 | 按管理员 ID 限制 |
| 问答测试 | `qa_test_per_minute` | 10 每分钟 | 按管理员 ID 限制 |

这里存在一个命名与实际语义的错位：创建会话实际用的是 `chat_per_minute` 的 20，单会话提问用的是 `session_per_minute` 的 10。README 和设计文档中的表述与源码不完全一致，本文以源码为准。

限流器是滑动窗口，数据存在进程内字典，每 300 秒清理一次超过 1 小时的空窗口。单机够用，多进程会各算各的。

### 11.3 已有安全控制

| 风险 | 控制 |
|---|---|
| SQL 注入 | DAO 使用参数化查询，动态字段来自白名单 |
| 上传路径穿越 | `safe_filename` 清理路径成分，文件落盘到固定目录 |
| 重复文件 | SHA-256 哈希唯一约束与本次上传去重 |
| 文件大小 | 单文件 5 MB，一次最多 20 个 |
| 文件类型 | 只接收 `.md` 与 `.markdown` |
| 暴力登录 | 登录 5 次每分钟 |
| 令牌伪造 | HMAC-SHA256 签名，常量时间比较 |
| 令牌过期 | 8 小时 TTL |
| XSS | 前端先转义再渲染，流式与完整消息都做转义 |
| 跨域 | CORS 只允许本地 5174 与 8010 |
| 错误泄露 | 500 响应只返回通用消息，详细堆栈只进日志 |

### 11.4 安全缺口

| 缺口 | 影响 |
|---|---|
| 默认管理员 `admin / 123456` | 生产环境可直接被登录 |
| `config.json` 内置开发用签名密钥 | 未设置 `SEMIKB_ADMIN_SECRET` 时会使用弱默认值 |
| 用户会话接口无鉴权 | 会话 ID 是自增整数，知道 ID 就能读取历史与评价 |
| WebSocket 令牌放在查询参数 | 可能进入浏览器历史、代理日志与访问日志 |
| 令牌黑名单只在内存 | 重启后登出令牌重新有效，多实例不共享 |
| `host=0.0.0.0` | 默认对局域网开放，没有 TLS 与反向代理 |
| 语料提示注入未专门过滤 | 如果文档正文包含指令性内容，可能影响生成 |
| 管理操作无独立审计表 | 登录、上传、删除只靠任务与日志，缺少不可篡改审计 |

### 11.5 性能设计

| 设计 | 作用 |
|---|---|
| 混合检索候选 20，最终 4 | 控制生成上下文与模型成本 |
| RRF k=100 | 两路排名融合，避免单路分数尺度问题 |
| HNSW `M=16`、`efConstruction=64`、查询 `ef=64` | 2168 条切片规模下足够，构建与查询平衡 |
| 嵌入批量 10，写入批量 50 | 减少外部 API 与 Milvus 往返 |
| 批量导入只 flush 一次 | 避免每篇触发 Milvus flush |
| 问答线程池与信号量 | 防止同步模型调用阻塞事件循环 |
| WebSocket 流式输出 | 降低首字等待的体感 |
| 管理台 `loadAll` 并行 | 首屏五个接口并行拉取 |
| 健康检查缓存 60 秒 | 避免频繁真实嵌入请求 |

### 11.6 可靠性设计

| 场景 | 当前行为 |
|---|---|
| MySQL 启动失败 | lifespan 记录异常，应用仍启动，健康检查显示 degraded |
| Milvus 启动失败 | 应用仍启动，检索与入库会失败，健康检查显示 degraded |
| 任务进程重启 | `recover_stale` 把 queued 与 running 任务标记失败，不自动重试 |
| 用户 WebSocket 断开 | 生成线程继续，结果仍落库，客户端可通过历史接口补看 |
| 管理端 WebSocket 断开 | 任务继续，重连后靠 REST 刷新 |
| 评分模型 429 | 保留召回结果，继续生成 |
| 生成模型失败 | 抽取式兜底 |
| 校验模型失败 | 引用完整性启发式 |
| Tavily 失败 | 联网文档为空，最终走无结果兜底 |

### 11.7 容量边界

当前容量判断基于 430 篇文档、2168 条切片、单机单进程。

- Milvus 当前规模很小，HNSW 与 BM25 查询压力不大。
- 主要瓶颈在 DashScope 嵌入与 LLM 调用，不在向量库。
- 四条知识问答实测平均 13087 毫秒，样本量仍小。直接回答耗时约 10 毫秒，不计入问答延迟。
- 管理台上传并发 2，批量脚本并发 4，再高会增加外部 API 429 概率。
- 8 路并发问答是设计值，没有做高并发压测，不能直接当作生产容量结论。

## 14. 已知问题与风险

### 14.1 按优先级列出

| 级别 | 问题 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| P0 | 默认管理员账号与默认签名密钥 | `init_db.sql` 种子为 `admin / 123456`，`config.json` 有开发密钥 | 生产可被直接登录或伪造令牌 | 上线前改口令、强制环境变量、移除默认密钥 |
| P0 | 用户会话接口无鉴权 | `/api/chat/sessions/{id}`、历史接口与 `/api/chat/sessions` 都不需要令牌，列表直接返回全部可展示会话 | 自增 ID 可枚举，也能从列表直接看到他人会话标题与预览 | 增加访客令牌或签名会话 ID，列表按访客隔离 |
| P1 | `max_llm_calls` 未强制执行 | `runtime.bump_llm` 只计数，节点没有预算检查 | 极端情况下模型调用次数不可控 | 在节点入口检查预算并终止 |
| P1 | 管理台问答测试没有外层超时 | `AdminService.qa_test` 直接调用 `runner.run` | 单次测试可能长时间占用线程 | 加 `wait_for` 与并发限制 |
| P1 | 限流配置命名与实际语义错位 | 创建会话用 `chat_per_minute`，提问用 `session_per_minute` | 文档与实现不一致，容量评估容易误判 | 重命名配置键并同步文档 |
| P1 | 重启只标记任务失败，不重试 | `TaskDao.recover_stale` 只更新任务状态 | 文档可能停在 parsing 或 indexing | 增加恢复策略与文档状态修复 |
| P1 | 删除先改状态，后删向量 | `AdminService.delete_document` 先 `mark_deleted` | 任务失败会留下 deleted 状态与残留向量 | 改为成功后置 deleted，或增加补偿任务 |
| P1 | 全量重建无失败回滚与清理 | `rebuild_all` 中途失败直接抛出 | 影子集合残留，文档状态可能混杂 | 增加失败清理与状态快照回滚 |
| P2 | 活跃集合指针文件是单点 | `active_collection.txt` 丢失后回退 v1 | 别名已切 v2 时，应用可能重新写 v1 | 以 Milvus 别名为主，文件只作缓存 |
| P2 | 同哈希上传存在并发竞态 | 先查 `get_by_hash`，再创建或更新 | 两个并发请求可能同时通过检查 | 加唯一约束冲突处理或数据库锁 |
| P2 | RRF 阈值 0，429 时保留全部召回 | `score_threshold=0.0`，评分限流时 `filtered=list(docs)` | 不相关文档可能进入生成上下文 | 校准 RRF 分数或增加轻量重排 |
| P2 | WebSocket 不自动重连 | `ChatSocket` 只在关闭时发事件 | 网络抖动后需手动重连，生成中回答不续传 | 增加指数退避重连与消息补偿 |
| P2 | LLM 健康检查只看密钥 | `HealthService._llm_health` 不发起真实请求 | 密钥存在但服务不可用时仍显示 up | 增加轻量真实调用或独立探针 |
| P2 | 构建脚本不清理旧 assets | `build_frontend.ps1` 只复制 | 静态目录会累积历史文件 | 构建前清理 `static/assets` |
| P2 | 预算配置与执行不一致 | 配置有 12 次调用预算，源码只统计不强制中断 | 接手者可能误判实际约束 | 在节点入口强制执行，并同步文档 |

### 14.2 需要特别说明的三个语义

1. `verified=true` 不等于回答完全正确。它表示 grounded 通过，回答是否有用还要看 `answers_question` 与 `terminated_by`。
2. `chunk_hard_max=2400` 不是所有切片的绝对上限。完整小节不超过 5000 字符时不会被切开。
3. 管理员令牌的登出只在当前进程有效。服务重启后，旧令牌会重新通过签名与过期校验。

### 16.3 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 建 Milvus 集合报 `TEXT field requires StorageV3` | 服务端未开启 `common.storage.useLoonFFI` | 使用 `VARCHAR(12000)`，不要改回 TEXT |
| 检索结果全部为空 | `score_threshold` 设成了 0.1 或更高 | 保持 0，依赖 RRF 排名与后续评分 |
| 评分频繁 429 | 评分模型太小或调用过密 | 使用 `qwen-plus`，降低并发，保留限流降级 |
| 文档页看不到新数据 | 前端构建产物未复制 | 重新执行 `build_frontend.ps1` 并确认 `static/index.html` 引用新哈希 |
| 分页控件不显示 | 总数不超过一页 | 属于预期行为，统计行仍会显示 |
| 管理台 401 | 令牌过期或签名密钥变了 | 重新登录，检查 `SEMIKB_ADMIN_SECRET` |
| MySQL 与 Milvus 数量不一致 | 入库中断、删除失败或未 flush | 跑 `verify_counts.py`，按 `doc_uid` 重建 |
| 服务重启后任务停在失败 | `recover_stale` 只标记失败 | 手动重建对应文档，后续补自动恢复 |

## 17. 总体评价

### 17.1 这套系统强在哪

- 闭环完整。入库、检索、生成、校验、引用、评价、审计、管理台都能跑通，不是只做了问答接口。
- 可追溯。回答不是一段孤立文本，背后有命中切片、路由、节点耗时、模型调用次数和终止原因。
- 检索方案务实。稠密加 BM25 加 RRF，适合术语密集的半导体文档，不依赖单一向量相似度。
- 参数落地。430 篇、2168 切片、两库计数一致、前端 22 页分页实测，都是可核对的事实。
- 代码分层清楚。`api`、`service`、`rag`、`ingest`、`dao` 责任明确，后续替换模型或存储不需要推倒重来。

### 17.2 这套系统还缺什么

- 安全还是演示级。默认口令、HTTP、查询参数令牌、内存黑名单，都不适合直接暴露到公网。
- 任务一致性还不够硬。重启、删除失败、全量重建失败都缺少自动补偿与回滚。
- 预算与超时没有完全统一。`max_llm_calls` 只统计不执行，管理台问答测试没有外层超时。
- 可观测性还停留在日志与统计页。没有指标、追踪、告警与标准评测集。
- 容量结论不足。四条知识问答样本不能代表真实并发表现。

### 17.3 适用判断

| 场景 | 判断 |
|---|---|
| 课程设计、毕业设计、项目答辩 | 很适合，功能完整，数据真实，讲解点多 |
| 单团队内网知识库 | 适合，需先改默认口令并限制网络暴露 |
| 公网生产服务 | 暂不适合，先补安全、任务一致性与可观测性 |
| 多实例高可用 | 暂不适合，进程内状态与单机 Milvus 需要重构 |
| 多格式文档平台 | 暂不适合，本期只支持 Markdown |

一句话总结：作为单机内网半导体知识库，这个项目完成度高、链路真实、可追溯性强；作为生产多实例系统，还差安全、任务一致性和可观测性三块硬工程。
